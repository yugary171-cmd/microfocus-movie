# 内容运营与事故处理

- 文档用途：定义日常内容操作、值班、止损、证据保全、恢复、对账和复盘流程
- 更新日期：2026-08-19
- 外部灰度前必须在发布工单中填写联系人、阈值、RTO/RPO 和通知渠道

本文是事故与值班手册，不替代 [release-checklist.md](./release-checklist.md) 的发布闸门，也不允许绕过 [architecture.md](./architecture.md) 的业务不变量。后台日常怎么登录、上剧、审核、发布，见 [后台管理系统操作说明](./admin-handbook.md)。当前仅允许 Mock 内部体验；真实 provider、生产构建和合规闸门未完成时不得执行外部放量。

## 1. 操作原则

1. **先止损，再定位**：高风险事故先熔断新奖励、新播放窗口或问题内容，不等待根因完全确认。
2. **服务端事实优先**：以 provider 可信结果、数据库事实、不可变账本和审计记录为准，不以客户端截图直接发奖、扣费或发布内容。
3. **不修改历史**：不覆盖 grant、debit、adjustment、回调、审核、版权和审计记录；纠错使用追加事实。
4. **不产生二次伤害**：不追扣形成负余额，不用数据库恢复做常规回滚，不把 Live 失败降级为 Mock 成功。
5. **最小恢复**：先恢复单一 provider、剧目或小流量，再逐级放开；监控暂时转绿不等于可以全量恢复。
6. **证据最小化**：工单只记录稳定 ID、时间、版本、查询和受控证据位置，不粘贴密钥、完整令牌、版权原件、回调原文或个人信息。

## 2. 角色与权限

| 角色 | 主要职责 | 不得执行 |
| --- | --- | --- |
| 事故指挥（IC） | 定级、分工、止损决策、升级、恢复批准和时间线完整性 | 同时独自审批自己的高风险补偿或证据删除 |
| 值班工程师 | 执行熔断、查询、修复、部署、回滚和技术验证 | 绕过业务状态机或直接改账本 |
| 内容合规负责人 | 版权/内容事故判断、停播意见、平台与权利方协调 | 在缺少新审核证据时批准重新发布 |
| 数据/账本负责人 | 确定影响范围、对账、补偿清单和恢复阈值 | 用汇总余额替代逐笔事实核验 |
| 安全/隐私负责人 | 评估秘密、越权和个人信息事件，决定法定/平台升级与通知 | 因影响用户少而跳过泄露评估 |
| 客服/运营 | 用户告知、工单归并、受控补偿申请和投诉升级 | 获取秘密、直接修改余额或承诺未确认结论 |
| 对外沟通负责人 | 统一用户、平台、合作方和监管沟通口径 | 发布未经 IC/合规确认的根因和影响数字 |
| 记录员 | 维护时间线、决策、证据位置和待办 | 在事故后重写或删除不利记录 |

值班人可以执行预授权的止损动作，不必等待完整审批。ADMIN 是管理 API 的执行角色，不等于可以独自批准高风险业务动作；除紧急止损外，执行人与批准人必须不同。

| 高风险动作 | 执行角色 | 最低批准要求 |
| --- | --- | --- |
| 开启熔断 | 值班工程师或 ADMIN | 可先执行，随后立即通知 IC 和领域负责人 |
| 解除熔断 | 值班工程师或 ADMIN | IC + 对应领域负责人；批准人不得是执行人 |
| 批量补偿/权益 adjustment | ADMIN | 数据/账本负责人 + IC；清单生成、复核和执行三者至少两人 |
| 批量回调重放 | ADMIN | 工程负责人 + 奖励账本或内容领域负责人 |
| 密钥应急撤销/轮换 | 值班工程师 | IC + 安全负责人；确认泄露时可先撤销后补审批 |
| 数据库恢复 | 数据库/工程负责人 | IC + 工程负责人 + 数据负责人共同批准 |
| 管理员应急恢复（全员无法登录） | 值班工程师 | IC + 安全负责人；改库时另加工程与数据负责人。规程见 [admin-emergency-access.md](./admin-emergency-access.md) |
| 事故后重新发布内容 | ADMIN | 内容合规负责人 + 独立 REVIEWER；执行人不得兼任审核人 |
| 隐私数据修复或重新处理 | 受授权工程师 | 安全/隐私负责人 + IC |

发布工单需记录主值班、备份联系人、各领域批准人和超期升级人。

## 3. 日常内容与运行流程

### 3.1 内容发布

1. EDITOR 创建剧目、填写权利资料元数据并上传受控材料引用。
2. EDITOR 为稳定集号创建媒体版本，从 API 获取短期签名后直传 VOD。
3. VOD 回调分别更新上传、转码和机审维度；失败时保存稳定错误码并进入可重试或人工处理状态。
4. REVIEWER 核对完整成片、权利范围、节目号、媒体文件 ID/版本和机审结果；不得审核本人创建或编辑的内容版本。
5. 权利有效且每个稳定集号的当前媒体版本均完成转码、机审、人工审核和微信视频发布后，剧目才可进入 `READY`。
6. 仅 ADMIN 执行发布；系统在发布事务内再次实时校验权利、媒体版本、审核职责分离和外部流量闸门。
7. 权利到期任务自动下架；紧急问题由 ADMIN 立即下架并停止新播放窗口。进程内每分钟运行一次，用 `BackgroundJobLease` 保证多实例只执行一次；过期 `ACTIVE` 权利改为 `EXPIRED`。同一定时器还会清除超过保留期的回调密文、删除超过 24 小时的限频桶，并对权益账本做周期对账。

业务记录只归档、失效或下架，不硬删除。版权材料原件存入限制访问的私有系统，数据库只保存受控对象引用、版本和校验摘要。

### 3.2 例行检查

- **每次发布前**：检查逐剧权利、当前媒体版本、审核记录、节目号、分享/直接链接和发布闸门。
- **灰度期间每日**：检查权利即将到期、回调积压、死信、奖励对账差异、投诉、熔断状态和容量余量。进程内对账若发现余额或完成 challenge 无 grant 的差异，会打开 `PROVIDER:LEDGER` 并暂停新奖励与锁定播放；不自动改写账本，需管理员关闭熔断。
- **持续监控**：登录/API 错误、播放启动、心跳、媒体交付、广告漏斗、异常发奖、错误扣费和 provider 状态。API 访问日志为单行 JSON，含 `requestId`、模块、稳定错误码、耗时和脱敏 actor/path；path/method/actor 按 `REQUEST_LOG_*` 上限截断；不含 Authorization、请求体、查询串或 `session_key`。健康检查与文档路由不记访问日志。生产不挂载 OpenAPI。
- **按发布工单周期**：验证备份可用性、证书/域名/密钥到期时间、管理员权限和离职回收。

每项检查必须有负责人、稳定查询或自动化命令、通过阈值和证据有效期。“大量”“异常”“尽快”等词必须在发布工单中量化。

## 4. 事故分级与响应目标

| 级别 | 示例 | 默认响应目标 |
| --- | --- | --- |
| SEV-1 | 资质/版权失效、内容安全事件、秘密或个人信息泄露、跨用户/管理员越权、大面积错误扣费或重复发奖、账本不可对账、生产数据损坏 | 5 分钟内确认，15 分钟内完成首个止损动作；立即通知 IC 和对应负责人 |
| SEV-2 | 单 provider 故障、回调持续积压、部分剧目不可播、广告/播放漏斗显著恶化但未发生资损 | 15 分钟内确认，60 分钟内完成隔离或明确降级 |
| SEV-3 | 单用户可恢复问题、低影响运营错误、未触发硬阈值的告警 | 当班处理或下一工作日进入排期 |

以上为默认上限。外部发布前应根据值班能力在发布工单中冻结更严格或经批准的目标；达不到承诺响应能力时不得扩大灰度。

发现者先记录事故 ID、发现时间、环境、候选版本、告警/用户入口和初始现象。IC 可随证据变化调整级别，但必须记录调整原因和时间。

## 5. 熔断范围与操作规则

- **全局奖励**：停止新 challenge 和发奖处理；保留已有正余额和待核验事实。
- **全局播放**：停止锁定内容的新租约/窗口；免费内容是否保留由事故类型和合规结论决定。
- **Provider**：隔离微信、VOD、CDN 或广告验证链路；Live 故障不得自动回退 Mock。
- **剧目**：停止指定剧目的目录曝光、奖励、新播放窗口和分享入口。
- **用户**：阻止风险用户创建 challenge 或锁定租约；不追扣、不产生负余额。
- **广告位**：停止指定广告位的新 challenge；其他广告位是否保留由影响范围决定。

每次开启、扩大、缩小或解除熔断必须写入审计：事故 ID、范围、原因、操作者、批准人、开始时间、复核时间和自动过期策略。安全默认是“可自动开启、不得无条件自动解除”；恢复必须满足第 8 节条件。

## 6. 通用事故流程

1. **确认与定级**：去除重复告警，确认环境、版本、时间窗口和用户/剧目/provider 范围。
2. **止损**：执行最小充分熔断；版权、安全、秘密和账本事故优先停止新访问或新写入。
3. **保全证据**：保存脱敏日志查询、稳定实体 ID、配置版本、构建哈希、审计记录和 provider 事件 ID；不改写原记录。
4. **建立时间线**：记录检测、决策、执行、状态变化、沟通和恢复节点，统一使用服务端时间并注明时区。
5. **定位根因**：区分代码、配置、数据、provider、权限、容量和人工操作；无法证明时标记为未知，不猜测成功。
6. **修复与离线验证**：在非生产或隔离数据上验证幂等、并发、失败重试和回滚。
7. **对账与用户保护**：确定受影响 challenge、grant、debit、reservation、媒体版本和用户，形成不可变纠错/补偿方案。
8. **小流量恢复**：先解除最小范围，观察冻结窗口；关键指标和对账稳定后再扩大。
9. **关闭与复盘**：记录最终影响、根因、修复、残余风险、责任人和截止日期。

禁止在事故中执行无条件 SQL 批量修改、删除审计/回调、手工伪造 provider 成功或直接把数据库恢复到旧时间点。

## 7. 专项处置手册

### 7.1 版权或内容安全

1. 立即将剧目下架并开启剧目熔断，停止目录、分享和新媒体窗口。
2. 保存当前权利版本、成片哈希、节目号、审核/发布记录、访问审计和投诉原文的受控引用。
3. 通知内容合规负责人；需要时按批准流程联系平台、权利方或监管方。
4. 核对是否影响同一权利方、同批媒体或其他剧目，必要时扩大熔断。
5. 只有新权利/媒体版本经过完整审核、合规负责人批准并完成小流量验证后才能重新发布。

### 7.2 奖励多发、少发或账本异常

1. 开启广告位、provider 或全局奖励熔断；若消费结算不可信，同时停止锁定内容新窗口。
2. 逐笔关联 provider 结果、challenge、callback event、grant、debit、reservation、adjustment 和广告结算。
3. 少发：优先完成原 challenge 的可信幂等发奖；无法满足原条件时，使用带原因、审批和 `Idempotency-Key` 的补偿 grant。
4. 多发未消费：追加 `FREEZE_REMAINDER`；确认可恢复时追加唯一 `RELEASE_FREEZE`。
5. 多发已消费：不制造负余额、不追扣未来权益；追加 `WRITE_OFF` 和事故记录完成财务核销。
6. 修复后使用脱敏事件验证重复回调、并发完成和补偿重放，再执行小流量恢复与全链路对账。

### 7.3 错误扣费或未确认播放

1. 停止受影响播放链路的新短媒体窗口，保留活动 reservation 和服务端媒体交付证据。
2. 核对租约、窗口授权/交付、心跳序列、播放状态、debit 和客户端版本；客户端缺少心跳不能单独证明已播放。
3. 确认未交付或错误扣费时追加补偿 grant，不修改原 debit；重复操作必须返回同一结果。
4. 已交付但无法确认播放时按未确认暴露恢复流程处理，不自动扣费，也不无限自动释放风险计数。
5. 恢复前验证暂停、缓冲、后台、断网、换设备和重复建租约场景。

### 7.4 播放地址或签名 Key 泄露

1. 停止新租约和媒体窗口，必要时开启全局播放或剧目熔断。
2. 撤销活动会话、执行 CDN 清理并轮换播放签名 Key。确认或合理怀疑 Key 泄露时立即撤销旧 Key，不保留兼容窗口；客户端通过重新鉴权取得新凭证。
3. 检查凭证 TTL、分段授权范围、IP/设备/会话异常、空 Referer、源码映射、构建物和日志泄露。
4. 量化旧地址最后可用时间；若超过发布时验证的最大停播窗口，保持 No-Go 并升级事故。
5. 重新启用前确认旧链接失效，客户端可处理 401/403 并重新申请租约，短窗口不会暴露整集。

### 7.5 回调积压或死信

1. 按 provider 开启奖励或媒体发布熔断，停止依赖未知结果推进业务。进入 `DEAD_LETTER` 时服务端会打开 `PROVIDER:VOD` 或 `PROVIDER:WECHAT`，不会自动打开 GLOBAL。
2. 核对积压量、最老事件年龄、验签结果、重试次数、ACK 行为和 provider 状态。`GET /v1/admin/callback-events` 列出积压元数据，不含加密载荷。
3. 敏感规范化载荷只在受控工具内解密；不得复制到普通日志或工单。超过 30 天保留期后，后台任务只清除密文和 schema，保留事件 ID、哈希与状态，不删除回调事实。
4. 修复后由 ADMIN 对指定事件执行受审计重放；状态从 `RETRYABLE_FAILURE/DEAD_LETTER` 原子迁回 `PROCESSING`，沿用原事件 ID 和幂等约束。若保留期内存在加密规范化载荷，服务端立即用该载荷执行；否则等待 provider 再次投递。不得复制新的业务事实。
5. 奖励晚到只有在可信 provider 证明广告于原 challenge 有效期内完成且仍处允许延迟窗口时，才能完成原 challenge；否则进入独立人工补偿。
6. 本次事故涉及的 provider、时间窗和事件批次死信必须清零；其他残留死信需逐笔归类且低于发布工单冻结阈值。相关媒体/账本状态对账和小流量验证通过后，才能解除熔断。

### 7.6 Provider 故障或广告无填充

1. 区分配置错误、认证失败、限流、平台故障和正常无填充；认证/验签失败不得自动重试。
2. 网络超时、5xx 和限流仅按有上限的指数退避与随机抖动重试，达到阈值后熔断。
3. 广告无填充、加载失败或用户未看完不发奖，保留既有权益并展示可理解提示。
4. VOD 故障时不把浏览器上传结果直接标记 READY，不签发无法验证的长期媒体地址。
5. Provider 恢复后先验证认证、回调、幂等和对账，再逐步解除熔断；严禁切换 Mock 作为外部降级。

错误分类（工单只用 class，不贴原始回调）：`ad_incomplete`、`ad_no_fill`、`ad_load_failed`、`reward_pending`、`reward_expired`、`playback_unconfirmed`、`playback_recover_cs`、`account_unavailable`。未知 `code` 记为 `unclassified`，并保留 `requestId`。核心漏斗事件名见契约 `FUNNEL_EVENTS`；客户端埋点去掉 token/secret/session_key。

### 7.7 认证、越权或秘密泄露

1. 立即禁用受影响账号/密钥，撤销会话并限制管理端和高风险 API；秘密不得写入事故工单。
2. 确定秘密类型、暴露时间、可访问范围、日志/构建物/仓库传播路径和已执行操作。
3. 按 [configuration.md](./configuration.md) 轮换 JWT、TOTP、微信、VOD、回调或播放密钥；TOTP 加密密钥使用双密钥窗口与 `totp:reencrypt`，验证完成前保持 `TOTP_ENCRYPTION_KEY_PREVIOUS`。
4. 审查管理员操作、导出、补偿、发布、下架和配置变更，保全不可变审计。
5. 完成权限修复、凭据撤销、构建物清理、会话重登和受影响方通知后，才允许恢复。

### 7.8 数据库故障或数据损坏

1. 停止奖励、权益消费、补偿和发布等高风险写入；只保留经证明不会使用陈旧授权的安全读路径。
2. 保存数据库、应用、迁移、部署和监控时间线，判断是不可用、延迟、容量、迁移失败还是逻辑损坏。
3. 应用发布失败优先回滚应用/配置或前滚修复，不能用数据库恢复覆盖发布后的合法写入。
4. 只有灾难恢复才能从备份恢复；执行前由 IC、工程和数据负责人确认恢复点、RPO、不可逆影响和补录方案。
5. 恢复后对 provider 事件、challenge、grant、debit、adjustment、reservation、审计和内容状态全量对账，再小流量开放写入。

### 7.9 隐私、注销或数据请求异常

1. 疑似个人信息泄露、跨用户访问或管理员越权默认按 SEV-1 处理，立即通知 IC 和安全/隐私负责人；仅有流程延迟且无越权/泄露证据时才可降为 SEV-2，并记录理由。
2. 立即停止相关接口、撤销受影响会话并限制数据导出；不得等待影响人数确认后才止损。
3. 保全请求 ID、账户状态变化、访问审计和处理任务，不把个人信息复制到普通工单。
4. 核对可删除数据、法定/安全保留数据和直接身份隔离；不得通过注销删除权益、版权、事故或管理员审计事实。
5. 修复后验证旧 JWT 拒绝、受限查询令牌、客服身份核验、删除/匿名化和处理结果查询。
6. 安全/隐私负责人立即启动届时适用的法定、平台和合同通知时限评估；是否通知用户、平台、合作方或监管方必须记录依据、决定人和完成时间。

### 7.10 管理员无法登录

管理面认证失败、验证器丢失或全部系统管理员锁定，按 [admin-emergency-access.md](./admin-emergency-access.md) 执行：优先由另一名健康管理员在后台重置凭据；全员不可登录时在受控主机运行 `npm run db:admin-break-glass`（先干跑，双人批准后再 `--commit`）。禁止隐藏登录入口、生产 `ADMIN_TEST_OTP` 或把 bootstrap / `ADMIN_BREAK_GLASS_*` 明文留在常驻 API 环境。

## 8. 恢复与解除熔断

解除任何熔断前必须同时满足：

- 根因、触发条件和失效控制已确认，并能解释已观察到的影响；未知根因不得恢复外部流量；
- 修复已经过非生产/隔离验证，回滚路径仍可执行；
- 影响范围、账本/内容/用户状态和待补偿清单已对账；
- 关键告警和回调积压恢复到发布工单阈值内；本次事故范围内的死信已清零，范围外残留死信均已归类和批准；
- 客服话术、用户恢复路径和必要通知已准备；
- 最小流量观察窗口内无重复问题，且至少两人批准扩大范围。

恢复顺序默认是：内部验证 → 指定账号/单剧目 → 最小灰度 → 分阶梯扩大 → 全量。每一步都记录开始/结束时间、指标、对账结果和继续/停止结论。

## 9. 用户沟通与补偿

- 客服工单使用 `requestId`、challenge ID、lease ID、drama ID 和脱敏用户 ID 定位；不得索取密码、验证码、完整 token 或密钥。
- 未确认结论统一表述为“正在核验”，不得承诺必定发奖、必定扣费撤销或具体根因。
- 单笔和批量补偿均需原因、范围、过期时间、审批人和 `Idempotency-Key`；先在脱敏清单中验证去重。
- 补偿不是删除原错误事实的替代品；原 challenge、grant、debit、adjustment 和事故 ID 必须可关联。
- 对外公告包含影响、用户应对、恢复状态和联系入口，不公开攻击细节、个人信息或内部安全配置。

## 10. 看板、告警与值班

看板至少展示：

- API/数据库：请求量、错误率、延迟、连接池、事务冲突和就绪状态；
- 播放：启动成功率、首帧、卡顿、心跳失败、短窗口签发、未确认暴露和凭证 401/403；
- 广告与权益：加载/开始/完成/可信验证/grant 漏斗、重复/失败发奖、余额差异和补偿；
- 内容与回调：发布/下架、权利到期、VOD 状态、积压、最老事件、重试和死信；
- 产品与风险：第二集完播、D1/D7、投诉、每锁定内容观看小时贡献毛利及全部熔断状态。

告警必须包含环境、版本、稳定错误码、影响对象、看板链接、操作手册入口和值班人；不得包含秘密或完整请求体。告警阈值、持续时间、去重、静默和升级路径在发布工单中冻结，并使用测试事件验证实际可达。

## 11. 灾难恢复、复盘与关闭

- 每次外部发布记录经批准的 RTO/RPO；备份频率和保留期必须能够支持该目标。
- 定期执行空白环境恢复演练，验证迁移、备份解密、完整性、恢复耗时及恢复点后写入的对账/补录。
- SEV-1 在恢复后 2 个工作日内形成复盘草案；SEV-2 在 5 个工作日内完成。复盘关注系统和流程，不以个人归责替代修复。
- 复盘至少包括：摘要、影响、时间线、检测缺口、根因、促成因素、止损效果、用户/财务/合规影响、恢复验证、做得好/需改进及行动项。
- 每个行动项必须有负责人、优先级、截止日期和可验证完成标准；高风险行动项关闭前不得扩大灰度。
- 只有对账完成、用户补偿/沟通完成、证据归档、残余风险接受和行动项登记后，IC 才能关闭事故。
