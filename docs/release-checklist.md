# 外部灰度与正式发布清单

以下清单中的“灰度启动前”项目是放量硬闸门；“灰度运行与停止”项目是在灰度启动后持续执行的目标和护栏，不构成启动前循环依赖。勾选人应在内部发布单中记录证据位置、核验日期和责任人，但不得把版权原件、证件或密钥提交到 Git。

产品节奏以 [product-plan.md](./product-plan.md) 为准：本轮是内部收口与内容验证，不是执行本清单做外部灰度。清单中的 500 激活、14 天、D7 5%、贡献毛利在没有真实 cohort 前视为**未校准护栏**，不能用 Mock 数据宣布成功或失败。

事故处置按 [operations.md](./operations.md) 执行。任何硬闸门未通过时结论只能是 No-Go，不得以口头承诺、临时关闭校验或切换 Mock 代替。

## 1. 发布记录与签字信息

- 发布类型：`外部灰度 / 扩大灰度 / 正式发布`（待填写）
- 候选版本、Git commit、构建编号与小程序版本：待填写
- 目标环境与计划窗口：待填写
- 发布负责人 / 工程复核人 / 产品负责人 / 内容合规负责人：待填写
- 数据负责人 / 安全与隐私负责人 / 值班人 / 回滚负责人 / 超期升级人：待填写
- 证据目录或发布工单：待填写（只记录受控位置，不粘贴秘密或版权原件）
- Go/No-Go 会议时间与最终结论：待填写

签字前必须确认所有证据都对应上述同一候选版本、同一生产配置和同一批内容；旧版本证据不得自动沿用。

发布类型适用规则：

- **首次外部灰度**：第 1–9、12–13 节全部适用；第 10 节在灰度启动后持续执行。
- **扩大灰度**：第 1–8、10、12–13 节全部适用，并重新确认第 9 节中仍然有效的内容、熔断和责任人条件。
- **正式发布**：第 1–8、11–13 节全部适用，并重新确认第 9–10 节的证据仍有效。
- 任何标记为 N/A 的检查项必须记录原因、影响和批准人；安全、合规、账本、真实 provider、回滚和签字项不得标记为 N/A。

证据标准：

- [ ] 发布工单为每项适用门禁记录唯一 ID、执行命令或查询、样本范围、观察窗口、通过阈值、证据时间和批准角色。可从 [acceptance-evidence-template.md](./acceptance-evidence-template.md) 复制表格。
- [ ] 回滚演练按 `sh scripts/rollback-drill.sh` 的只读清单执行，并在工单记录 RTO/RPO；不用数据库恢复做常规回滚。
- [ ] “为 0”“重大”“大面积”“明确余量”“可接受”等表述均已在本次发布工单中转换为可判定阈值，未量化时不得据此签署 Go。
- [ ] 所有自动化结果、看板截图和查询记录均能追溯到候选版本与目标环境，并在 Go/No-Go 时仍处于约定有效期内。

## 2. 主体、备案和平台

- [ ] 企业主体、小程序认证与小程序备案完成。
- [ ] 微信实际服务类目获批，属地广电准入或纳管路径取得书面确认。
- [ ] 微信流量主、激励视频广告位及届时有效的广告规范完成确认。
- [ ] 隐私指引、用户协议、广告权益规则、客服和版权投诉入口完成审核。
- [ ] `admin` 网站 ICP 备案完成；`api`、`media` 子域名完成 HTTPS 和微信服务器/下载域名配置。
- [ ] 未成年人保护、适龄提示及其他届时适用要求已由内容合规负责人确认，结论和依据有记录。
- [ ] 再次核对上线当日生效的广电、工信部和微信规则；征求意见稿不当作正式依据。

## 3. 每部剧的发布证据

- [ ] 所有版权授权书、发行许可证及合规承诺函的原件扫描件，已存入受控的企业私有云盘或确定的合规系统中，发布工单中仅记录文档链接。
- [ ] 发行许可证或上线报备号与成片版本一致。
- [ ] 授权主体、期限、地域和权利链有效。
- [ ] 授权明确覆盖微信小程序传播、广告变现、转码、截图、封面和宣传物料。
- [ ] 总集数、稳定集号、片名、字幕和展示的节目号一致。
- [ ] VOD 转码、内容机审、人工复核和微信视频发布全部通过。
- [ ] 每个实际发布媒体版本已完成审核记录；允许同一内容编辑既提交又审核。权利、媒体和外部流量闸门仍须全部通过。
- [ ] 权利到期自动下架任务已经创建并演练。
- [ ] 版权投诉、内容举报、紧急下架和重新发布流程已验证；联系人、处理记录和证据保全位置明确。
- [ ] 未发布、Mock、权利失效或已下架内容不能被目录、搜索、直接链接或分享卡片访问。

## 4. 构建物、配置与部署

- [ ] `NODE_ENV=production`、`WECHAT_MODE=live`、`VOD_MODE=live`。
- [ ] 四项 `COMPLIANCE_*` 均为 `true`，并由两人复核证据。
- [ ] 微信小程序版本、管理端和 API 构建均来自发布记录中的同一 Git commit；依赖锁文件未漂移。
- [ ] typecheck、单元测试、构建、数据库迁移、HTTP 烟测和敏感信息扫描在候选版本上重新执行并留存结果。
- [ ] 构建产物校验值已记录；正式包不包含 Demo 媒体、Mock 数据、测试账号、调试入口、公开可访问的源码映射或内部体验标识。
- [ ] 生产域名、环境变量、微信合法域名和 VOD 配置均来自受控配置源；不存在手工临时值。
- [ ] 微信、腾讯云和防盗链凭据由密钥管理注入，仓库和构建产物中无秘密。
- [ ] 激励广告使用可信服务端验证或可信回调；`client_attestation` 未进入外部灰度或生产配置。
- [ ] 数据库迁移采用 expand/contract 或其他已批准的向后兼容策略，新旧应用版本的兼容窗口已验证。
- [ ] 常规发布回滚只回退应用/配置或执行前滚修复，不用数据库恢复覆盖发布后新增的权益、审计或业务记录。
- [ ] 数据库备份恢复仅作为灾难恢复演练；已验证恢复点之后写入的对账、补录、用户权益保护和审计保全流程。
- [ ] 小程序提审版本、审核结果、体验版与最终发布版本一致；发布后可核对线上版本号。

## 5. 安全、权限与数据保护

- [ ] 管理员强密码、TOTP、最小角色、离职回收和审计告警已启用。
- [ ] VOD 回调签名、短期上传签名、120 秒播放凭证和 Key 防盗链已在真实环境验证。
- [ ] WAF/API 网关、速率限制、备份、恢复、日志脱敏和告警已经演练。
- [ ] 完成依赖漏洞检查、密钥扫描和管理员越权测试。
- [ ] 使用空白 MySQL 执行 `npm run db:migrate:deploy`，再用脱敏测试数据完成登录、权益、播放和后台 HTTP 烟测。
- [ ] 日志、埋点、客服记录和审计数据不包含微信 `session_key`、密钥、完整令牌、完整请求体或非必要个人信息。
- [ ] 个人信息、广告挑战、权益账本和审计日志的保留矩阵已经负责人批准；账号注销、可删除数据清理和必要记录隔离已完成端到端验证。未批准前以 [privacy-retention-matrix.md](./privacy-retention-matrix.md) 为准，清理作业必须保持阻断。
- [ ] 数据访问、导出、删除、匿名化和管理员审计权限均通过越权与最小权限验证。

## 6. 用户主路径与异常体验

- [ ] 首页、搜索、剧目详情、免费试看、显式登录、广告解锁、恢复播放和历史续看完成真机端到端验收。
- [ ] 登录取消或失败不影响免费浏览；成功登录后保留目标剧集和播放进度。
- [ ] 用户能看到奖励时长、约可看集数、有效期和仅限本剧；验证中、失败、无填充和明确频次限制具有不同提示。
- [ ] 基础分享只对已发布且权利有效的内容开放；客服/反馈入口可提交 challenge ID 并完成奖励未到账处理闭环。
- [ ] 客服话术（如：奖励延迟、无广告填充的解释）与人工补偿 SOP 已定稿，一线客服/运营人员已完成培训并具备对应后台权限。
- [ ] 账号注销、个人信息查询/删除、用户协议、隐私指引和广告权益说明均可访问并正常工作。
- [ ] iOS/Android 微信真机、弱网、窄屏、全面屏和前后台切换通过。

## 7. 权益账本、播放与广告对账

- [ ] 重复奖励、负余额、未完整广告发放、暂停/缓冲/后台误扣均为 0。
- [ ] 并发设备、挑战重放、心跳重试/乱序、额度到期和跨集消费测试通过。
- [ ] 广告无填充、用户中途关闭和 API/VOD 故障均有可恢复提示。
- [ ] 下架或熔断后立即停止签发新播放凭证；已签发凭证的最坏残留播放窗口不超过已验证的 120 秒。
- [ ] 若法规、平台或事故级别要求快于 120 秒停播，CDN 清理、密钥轮换或活动会话撤销等加速机制已经验证，并记录实际最坏停播时间。
- [ ] 广告 challenge、可信回调、权益 grant、消费记录和人工补偿可通过稳定 ID 逐笔关联。
- [ ] 同一 challenge 的完成重试和回调重放保持幂等；人工补偿重复请求不会产生重复权益。
- [ ] 锁定内容使用服务端可观测的短媒体窗口和权益预留；停止心跳后不能继续取得新窗口，反复创建租约不能清除预留或绕过扣费。
- [ ] 暂停、缓冲、后台和服务端确认未交付的窗口会释放预留且不扣费；已交付但未确认的暴露达到阈值后会阻断新窗口并进入恢复流程。
- [ ] 重装/换设备后可查询旧租约和未确认窗口；自动宽限有滚动上限，重复未确认播放会转客服核验而不会永久静默锁死或无限释放。
- [ ] 冻结、释放冻结与并发消费使用同一事务锁定顺序；adjustment 重放幂等，累计释放量不会超过对应冻结量。
- [ ] 发布前使用脱敏测试数据完成“广告平台结果 → challenge → grant → 剩余余额 → 播放心跳消费”的全链路对账。
- [ ] 灰度期间已安排广告平台结算与内部奖励账本的周期对账；差异阈值、负责人和暂停发奖条件已写入发布工单。

## 8. 指标、监控与值班

- [ ] 数据埋点能计算激活、第二集完播、广告漏斗、D1/D7、卡顿、投诉和单位贡献毛利。
- [ ] 广告漏斗能区分点击、拉起、完整结束、可信验证、权益到账和广告后继续播放；事件分母、去重和观察窗口已冻结。
- [ ] 生产看板至少覆盖登录、API 错误、播放启动、卡顿、心跳失败、广告加载/完成/发放、奖励异常、投诉、VOD 回调和全部熔断状态。
- [ ] 回调积压、最老未处理年龄、重试次数和死信数量具有看板与告警；死信重放经过权限、审计和幂等验证。
- [ ] 回调在 ACK 前已持久化重放所需的加密规范化载荷；验证过“死信 → 修复 → 原事件重放 → 对账”，以及符合/不符合晚到奖励条件的两条路径。
- [ ] 每项关键指标具有负责人、告警阈值、通知渠道和升级路径；已通过测试事件验证告警能够到达值班人。
- [ ] 灰度观察窗口、值班排班、每日复盘时间、事故分级和对外沟通负责人已写入发布工单。
- [ ] 按计划灰度规模完成容量或负载验证，数据库连接、API、回调和媒体链路具有明确余量与降级方案。

## 9. 灰度启动前条件

- [ ] 首轮仅使用 5–10 部合规剧目和私域/自然流量。
- [ ] 已配置全局、用户、剧目和广告位熔断；值班人知道如何操作。
- [ ] 灰度流量来源、用户范围、放量步骤和单步观察窗口已确定；每一步都可独立暂停或回退。
- [ ] 产品、工程、内容合规、数据和值班负责人已完成 Go/No-Go 复核，发布记录中不存在“待填写”或未关闭的阻塞项。
- [ ] 已确认正式发布不会因 500 激活、14 天、D7 等灰度运行期指标形成启动前循环依赖。

## 10. 灰度运行与停止条件

- [ ] 首轮灰度目标为至少 500 名激活观众并运行不少于 14 天；该数字是未校准的观察目标，不用于启动前验收。
- [ ] 第一个完整真实 cohort 只用于建立基线；第二个 cohort 启动前已冻结继续、迭代和停止阈值。
- [ ] 每次扩大流量前重新检查资质、内容权利、重大告警、奖励对账、投诉和单位经济，不按日历自动扩量。
- [ ] 扩大灰度前，上一流量阶梯已完成预定观察窗口并达到冻结的继续阈值；下一阶梯的用户范围、容量余量和回退点已经批准。
- [ ] 任何资质失效、平台严重警告、版权或内容安全事件均立即停止新凭证并启动停播流程；实际完成时间符合第 7 节已验证的最大残留窗口。
- [ ] 错误扣费、重复发奖、奖励不到账或账本差异超过发布工单冻结阈值时，立即熔断对应播放或奖励链路。
- [ ] 连续两轮 D7 低于 5%，或连续两个完整 cohort 贡献毛利为负，则停止扩量并重新评估规则。
- [ ] 广告收入先按预估值监控，贡献毛利最终结论以官方结算报表为准；结算未完成时不得宣布单位经济成立。

## 11. 正式发布升级条件

- [ ] 至少完成一个基线 cohort 和一个按预先冻结阈值评估的后续 cohort。
- [ ] 后续完整 cohort 实际达到预先冻结的“继续并转正式发布”阈值；仅达到“迭代”或未达到阈值时结论必须为 No-Go 或继续灰度。
- [ ] 正式发布阈值冻结时已定义最低有效样本、数据完整率、归因规则、观察窗口和广告结算成熟度，评估过程没有事后修改口径。
- [ ] 核心性能指标（如：无崩溃会话率、视频首帧秒开率、播放卡顿率）已建立基线，且符合正式发布预期。
- [ ] 产品负责人已基于真实行为数据确认目标用户、核心漏斗和继续/停止阈值，不再把未校准护栏当作正式成功线。
- [ ] 官方广告结算可用于核算单位贡献毛利，且未触发连续两个完整 cohort 贡献毛利为负的停止条件。
- [ ] 没有未关闭的版权、内容安全、隐私、重复发奖、错误扣费或重大稳定性事故。
- [ ] 客服、投诉、奖励补偿、内容下架、值班和事故响应在灰度中实际运行并完成复盘。
- [ ] 重新核对主体、平台规则、逐剧权利、生产配置、构建版本和所有灰度启动前硬闸门。
- [ ] 产品、工程、内容合规、数据和运营负责人共同签署正式发布 Go 决定。

## 12. 回滚、停播与恢复

- [ ] 已演练应用版本回滚、配置回滚和数据库前滚修复，并记录本次发布批准的 RTO/RPO、测量结果及批准人。
- [ ] 数据库恢复只用于灾难恢复，不作为常规版本回滚；恢复演练包含恢复点后权益、审计和业务写入的对账与补录。
- [ ] 已演练全局、用户、剧目和广告位熔断；回滚时停止新租约、新奖励或问题内容，不删除权益账本和审计记录。
- [ ] 内容事故可立即下架并停止新凭证；奖励事故可暂停新 challenge，同时保留用户已有正余额。
- [ ] 回滚后能够核对受影响 challenge、grant、消费与补偿范围，并向受影响用户提供反馈和恢复路径。
- [ ] 恢复前必须完成根因确认、修复验证和小流量复开；涉及回调或事件处理时还必须完成脱敏事件重放。不得仅因监控暂时恢复正常而直接全量。
- [ ] 发布失败、停播、恢复及用户沟通均记录时间、操作者、原因、证据和最终结论。

## 13. 最终签字

- [ ] 发布负责人确认候选版本、执行步骤和回滚步骤一致。
- [ ] 工程复核人确认测试、构建、迁移、安全和监控证据有效。
- [ ] 内容合规负责人确认主体、规则和每部剧发布证据有效。
- [ ] 安全与隐私负责人确认秘密、权限、个人信息、注销和事故升级流程有效。
- [ ] 数据负责人确认指标、对账、观察窗口和停止阈值可执行。
- [ ] 产品负责人根据本次发布类型签署 `Go / No-Go / 延期复核` 结论。
